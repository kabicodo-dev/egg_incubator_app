PROPOSED HW-02 Protocol\n\n### A.1 Wire model (proposed)\n\n- **Transport:** USB serial, **9600 baud**.\n- **Framing:** newline-delimited JSON. Each frame is exactly **one JSON object** terminated by a single **`\\n`**. Any `\\r` is a legacy artifact of `Serial.println` and is stripped by the legacy sketches; the proposed contract uses **`\\n` only**.\n- **Direction:** `APP -> FW` (Command / Hello) and `FW -> APP` (Telemetry / Ack / Hello-ack / Event).\n- **Identities:** App assigns `id` (any string ≤ 23 chars); each side correlates by `id`; `ack.id` echoes the command `id`.\n- **Correlation rule:** an `ack` with a given `id` is the sole asynchronous confirmation that the *command was processed*; it is **not** proof that a relay physically switched. `hardwareVerified` is false on reference HW.\n- **Split frames:** not required. The proposed protocol keeps **one JSON frame per message** (a single frame carries all state). The legacy `STATUS,...` plain-text output of `SmartHatch_Uno.ino` is **LEGACY** and is not part of the proposed contract.\n\n> **Important — hardware buffering vs. application-level capacity (separately defined).**\n> - **UART RX buffer:** the AVR `HardwareSerial` RX ring buffer is **64 bytes**. This is a fixed hardware limit; a frame longer than 64 bytes arriving over USB serial will overrun the RX buffer **regardless of the firmware's application-level parse buffer**.\n> - **Application-level parse capacity:** this is the buffer the firmware code uses to hold one parsed frame before it is processed. The legacy Uno sketch uses `serialLine[48]`; the modern `SmartHatch_Uno.ino` uses `CMD_BUFFER_SIZE = 160`; the combined sketch uses `serialLine[120]`. These are **not** the same as the 64-byte RX ring buffer, and they are not interchangeable.\n\n### A.2 Message families\n\n| Family | Direction | Mandatory fields | Optional / errors |\n|---|---|---|---|\n| **Command** | APP → FW | `type`=`\"command\"`; `id` (≤23 chars); `payload` (object) | `id` duplicate → re-play with `replay` flag; unknown `payload.key` → `{\"error\":\"UNKNOWN_KEY\"}` (400-class text in `ack.json.status`) |\n| **Telemetry** | FW → APP | `type`=`\"telemetry\"`; `device` (≤31 chars); `u` (monotonic uptime µs, uint64) | `sensors` object with `i`/`b` valid booleans and temperature/humidity (float null if invalid) |\n| **Ack** (reply to Command) | FW → APP | `type`=`\"ack\"`; `id` (echo of command `id`); `status` (200/400/409/replay) | `error` human-readable string; `hardwareVerified` (always false on reference HW) |\n| **Hello** | APP → FW | `type`=`\"hello\"`; `payload` (see §A.3) | — |\n| **Hello-ack** | FW → APP | `type`=`\"hello_ack\"`; `message` (`\"accepted\"` / `\"rejected:<reason>\"`) | — |\n| **Event** | FW → APP | `type`=`\"event\"`; `code` (stable enum); `payload` (object) | — |\n\n### A.3 HELLO (proposed)\n\n```\nAPP -> FW : {\"type\":\"hello\",\"payload\":{\"hardware\":\"SmartHatch Uno\",\"board\":\"UNO_R3\",\"firmwareVersion\":\"1.0.0\",\"protocolVersion\":\"0.2.3\",\"baudRate\":9600,\"deviceToken\":\"<persistent 32-byte hex nonce>\"}}\nFW -> APP : {\"type\":\"hello_ack\",\"message\":\"accepted\"}\n```\n\n- `deviceToken` is **PROPOSED**: a 16-byte random nonce persisted in EEPROM (address 0x100–0x10F) at first boot; absent → empty string (rejected by backend).\n- `protocolVersion: \"0.2.3\"` is the **PROPOSED HW-02** version, not the legacy firmware's.\n\n### A.4 Command payload (proposed)\n\n```\nAPP -> FW : {\"type\":\"command\",\"id\":<23-char>,\"actuator\":...,\"state\":...}\n```\n\n- Allowed `key` set (no expansion without a formal protocol version bump): `chosenEgg`, `incubationDay`, `brooderStart`, `setPoint` (via relay state), `turnNow`.\n- **Duplicate `id`:** FW replies `{\"type\":\"ack\",\"id\":<id>,\"status\":\"replay\",\"error\":\"DUPLICATE_ID\"}` and **does not re-apply** the side effect. This is the **only** way the app can de-duplicate without trusting a re-sent command.\n- **Error handling:** FW never answers an unknown key with a 5xx; it answers `status:\"400\"`, `error:\"UNKNOWN_KEY:<key>\"`.\n\n### A.5 Telemetry (proposed)\n\n```\nFW -> APP : {\"type\":\"telemetry\",\"device\":\"UNO_R3\",\"u\":<uint64 uptime µs>,\"sensors\":{\"i\":{\"valid\":true,\"temperature\":37.4,\"humidity\":51.2},\"b\":{\"valid\":true,\"temperature\":31.1,\"humidity\":49.0}}}\n```\n\n- `valid` = fresh physical reading (within `sensorStaleAfter`); false iff the DHT11 reports NaN/out-of-range.\n- Values are **null** when the sensor is invalid — never `0`.\n\n### A.6 Event (proposed)\n\n```\nFW -> APP : {\"type\":\"event\",\"code\":\"SENSOR_INVALID\",\"payload\":{\"sensor\":\"i\",\"time\":<monotonic µs>}}\n```\n\nStable codes: `SENSOR_INVALID`, `BATCH_STARTED`, `TURN_STOPPED` (lockdown), `RELAY_STATE` (optional relay snapshot, included only on explicit poll).\n\n### A.7 Read-only STATUS, STATE and retained EVENT replay (defined)\n\n- **Physical START / STOP** are *state changes*, not standalone wire frames in the proposed JSON catalog. In the reference firmware these are carried as `STATUS,...` plain-text lines (LEGACY) and as relay state in `telemetry.actuators` (proposed). The proposed catalog has **no** `START`/`STOP` frame; control actions arrive as `command` frames from the app, and the `ack` confirms processing only.\n- **Read-only STATUS:** the proposed protocol has **no** read-only `status` frame. The closest read-only source of truth on the wire is `telemetry` + `event`; the modern reference firmware emits these asynchronously and never waits for an app request. The legacy `STATUS,...` line is excluded from the proposed contract.\n- **STATE:** the proposed catalog carries state only inside `telemetry` (`actuators`, `turning`) and through `event` codes. There is no separate `state` object; stateful facts are replicated in `telemetry` and, where durability matters, in the EEPROM manifest.\n- **Retained EVENT replay:** events are one-shot wire records (no in-memory replay). Replay semantics are provided at the app layer by `ack.id` for commands only. `event` records are consumed on arrival and **not** retained by the firmware; a power cycle discards them. The app may re-read `telemetry` to reconstruct current state.\n- **Correlation:** `ack.id` echoes the `command.id`; `hello`/`hello_ack` complete the link-establishment handshake; `telemetry`/`event` carry `device` and `u` for ordering and loss detection by the app.\n- **Duplicate handling:** an in-flight `command` whose `id` is already being processed is replied with `status:\"replay\"`, `error:\"DUPLICATE_ID\"`, and its side effect is **not** re-applied. The app de-duplicates from `ack.id` only.\n- **Recovery:** power-loss and serial-interruption recovery is defined in `HW-02_Uno_Feasibility_And_Recovery.md` §5 (durable `commandAckSeq`, per-batch manifest, journal-before-write, corrupted-Seq reset, TIMEOUT/PORT_CLOSED states). It is **PROPOSED**, not implemented.\n\n### A.8 Frame byte counts (CALCULATED, including LF)\n\nCompact JSON (`json.dumps(..., separators=(\",\", \":\"))`) and the maximum permitted field lengths from §A. `u` is measured at the uint64 maximum `18446744073709551615`; `error` at `MAX_ERROR_LENGTH`; `id` at 23 characters; `device` and `actuator` at their declared maxima.\n\n| Frame | Max bytes incl.
