Wire-frame fit against the UNO limits — RX buffer vs. app-level buffer\n\nThis section deliberately **separates the UART hardware buffer from the firmware application-level parse buffer**.\n\n| Family | Max frame (CALCULATED) | UART RX ring buffer (64 B, hardware) | App-level parse buffer | Fits RX? | Fits app buffer? | Verdict |\n|---|---|---|---|---|---|---|\n| Legacy `ACK,<msg>` / `STATUS,...` | ≤ 48 B | OK | `serialLine[48]` OK | OK | OK | LEGACY |\n| Proposed JSON **Command** (92 B) | 92 | **No** | `CMD_BUFFER_SIZE=160` OK | **No** | OK | **BLOCKED** (RX overrun) |\n| Proposed JSON **Telemetry** (184 B) | 184 | **No** | app buffer OK | **No** | OK | **BLOCKED** (RX overrun) |\n| Proposed JSON **Ack** (128 B) | 128 | **No** | app buffer OK | **No** | OK | **BLOCKED** (RX overrun) |\n| Proposed JSON **Hello** (191 B) | 191 | **No** | app buffer OK | **No** | OK | **BLOCKED** (RX overrun) |\n| Proposed JSON **Hello-ack** (42 B) | 42 | OK | app buffer OK | OK | OK | **BLOCKED** (still proposed; but RX fits) |\n| Proposed JSON **Event** (94 B) | 94 | **No** | app buffer OK | **No** | OK | **BLOCKED** (RX overrun) |\n\n**Corrected conclusion:** every proposed JSON frame is measured by the corrected script (`HW-02_count_frames.py`) with compact JSON + LF. The **64-byte UART RX ring buffer is a hard hardware limit** and overrun occurs on the wire before the firmware's application-level parse buffer is ever consulted. The firmware's app-level capacity (`serialLine[48]`) is a separate, fixable software constraint and is **not** the cause of the RX overrun. All proposed frames **EXCEED** the agreed hardware RX capacity and are therefore **BLOCKED**.\n\n> **How the app-level capacity differs (requirement 6).** The RX ring buffer is owned by `USART_RXB` in hardware and is not under firmware control; it cannot be enlarged from sketch code. The application-level parse buffer (`serialLine`/`CMD_BUFFER_SIZE`) is a software choice — the legacy Uno's `serialLine[48]` overflows on 92-byte frames, so the modern Uno sketch's `CMD_BUFFER_SIZE = 160` is a sufficient fix for that software constraint. But the 64-byte RX limit is fixed, so a larger app buffer does **not** rescue frames that exceed 64 bytes. A frame that exceeds 64 bytes will be dropped by the RX hardware even if the app-level buffer is 4096 bytes. **Only reducing the frame size, adding framing-aware buffering in the host, or changing the transport (e.g. a binary protocol with explicit framing and joint agreement) can resolve this BLOCKED state.**\n\n---\n\n## 5. Durable command/event identity and recovery (corrected, fully defined)\n\n### 5.1 Durable identity\n\n| Item | Legacy firmware | Proposed HW-02 |\n|---|---|---|\n| Ledger | none | 32-byte `deviceToken` at EEPROM 0x100–0x10F, written once at first boot; `hello` reports it |\n| Manifest | none | per-batch EEPROM: magic, version, eggType, epoch/day, `commandAckSeq` (monotonic uint32) |\n| Correlation | legacy sketch: `ackCache[8]` (volatile) | **PROPOSED**: a **durable** `commandAckSeq` + a per-batch manifest; the combined sketch's 8-entry volatile cache is **not** durable and is **not** atomic |\n\n### 5.2 Physical START / STOP, read-only STATUS, STATE, retained EVENT replay (defined)\n\n| Concept | Definition (proposed HW-02) |\n|---|---|\n| **Physical START** | Not a wire frame. In the proposed catalog it is a `command` frame (`type=command`, `id`, `payload` selecting the batch), answered by `ack`. The hardware-side `START` is represented in `telemetry.actuators`/`turning` and the EEPROM manifest, not in a standalone STATUS packet. |\n| **Physical STOP** | Not a standalone frame. Stopped state is conveyed by `telemetry` (`actuators` false / `turning.active=false`) and by `event` codes (`TURN_STOPPED` at lockdown). No read-only `status` frame exists in the proposed catalog. |\n| **Read-only STATUS** | No `status` frame in the proposed catalog. The read-only source of truth on the wire is `telemetry` + `event`. The legacy `STATUS,...` line is excluded. |\n| **STATE** | Carried only inside `telemetry` (`actuators`, `turning`) and through `event` codes. No separate `state` object. |\n| **Retained EVENT replay** | Events are one-shot wire records. **No firmware-side replay**. Replay semantics are command-only (`ack.id` + `DUPLICATE_ID`). The app may re-read `telemetry` to reconstruct current state after reboot. A power cycle discards `event`s. |\n| **Correlation** | `ack.id` echoes `command.id`; `hello`/`hello_ack` complete link establishment; `telemetry`/`event` carry `device` and `u` for ordering and loss detection by the app. |\n| **Duplicate handling** | A `command` whose `id` is already being processed is replied `status:\"replay\"`, `error:\"DUPLICATE_ID\"`; side effect **not** re-applied. The app de-duplicates from `ack.id` only. |\n| **Recovery** | Defined in §5.3. PROPOSED, not implemented. |\n\n### 5.3 Recovery behavior on power loss\n\n| Failure | Legacy hardware | Proposed HW-02 |\n|---|---|---|\n| Overrun (line too long) | drops the line (`serialLineLength=0`) | PROPOSED: reply `{\"error\":\"E2BIG\",\"status\":\"400\"}` and reject; no frame consumed |\n| No frame at all | — | PORT_CLOSED / TIMEOUT → `disconnected` state |\n| Partial frame (unterminated) | held in buffer | PROPOSED: drop when overrun or on TIMEOUT |\n| Power loss inside `EEPROM.write`/`put` | torn write observable | PROPOSED (H1) journal/validate before accept |\n| Boot with corrupt `commandAckSeq` | — | PROPOSED: reset to BATCH_START; app resyncs via `GET_STATE` |\n\n### 5.4 Two-EEPROM.update calls guarantee atomic recovery\n\n**NO.** Two `EEPROM.update` calls are **not** an atomic pair, and a volatile `ackCache` is **not** durable. A power cut between the two updates leaves `version`/`day` inconsistent. **Durable recovery requires:** a single-writer manifest (`magic` + `version` + `day` written together) + a CRC/journal before every write, and an app-side `commandAckSeq` handshake. This is PROPOSED, not implemented.\n\n### 5.5 Outstanding open decisions carried forward (unchanged)\n\n- **RTC / wall-clock** — missing in both sketches; `millis()`-based monotonic used for day counting; a real-time clock + clock-sync command only if wall-clock semantics are required. **MISSING**.\n- **Offline authorization** — no auth on the wire. App-readable `hello` identity only; **offline auth is not provided** in this HW-02 pass. **NOT PROVIDED**.\n- **Authenticated cloud-receipt release** — no public-key/device-cert chain on Uno.
