### B. Verification/reset flow — separately authorized Auth effects

Only after exact per-user action scope is approved, use consenting disposable
**test** accounts to test verification/resend and password recovery. These flows
can alter users, credentials or sessions and consume one-time tokens; SMTP-only
permission must not silently include them. If current unchanged confirmation or
redirect settings prevent a valid check, mark BLOCKED rather than edit them.

- Verification reaches the correct user, opens only the already approved route,
  and enforces supported expiry/replay behavior; no token in evidence.
- Reset is requested with explicit test-account-owner permission; verify recovery
  route and password login afterward, without team reapproval. Never reset a real
  farmer/team production account for this check or log either password.
- Ordinary email/password login sends no email code. Signup/verification alone
  does not assign incubator records. Account-access checks require their own
  authorized implementation/fixtures and cannot be passed by mail delivery.
- Throttling, resend, invalid credential and SMTP outage tests require bounded
  fault-injection permission; do not intentionally break the shared test sender.

1. Stop test dispatch. Preserve sanitized errors and distinguish unsent, accepted,
   delivered and unknown outcomes. Already delivered email cannot be recalled;
   reverting SMTP does not invalidate links or undo any Auth action.
2. Restore only the exact previously recorded test-project SMTP fields/state via
   the supported configuration method. If SMTP was originally disabled, restore
   that state; the default sender's recipient/rate restrictions then apply again.
   If a previous secret is unrecoverable, do not overwrite that setup: BLOCKED
   before execution until the authorized owner supplies a secure rollback method.
3. Read back non-secret configuration and compare baseline, including unchanged
   signup/other Auth settings. Restore any unintended non-SMTP drift only within
   explicitly approved rollback scope, otherwise stop and escalate for authorization.
4. Custodian revokes this experiment's dedicated App Password after sender rollback
   and confirms no other authorized service depends on it. No broad password/security
   reset and no revocation of unrelated App Passwords.
5. No users, records or fixtures are created in stage A, so no database cleanup.
   Stage B needs a separate approved account/session cleanup plan; token/session
   revocation or user deletion is not covered automatically by SMTP rollback.
6. Never fall back to the application project, relink/reset/migrate Supabase, erase
   historical evidence or interact with the occupied Arduino while troubleshooting.
