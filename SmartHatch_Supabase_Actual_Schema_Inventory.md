## Summary for Kath

- The real database has **four application tables**, with **22 columns** total.
  The app calls batches **sessions** in the database: `public.incubator_sessions`.
- Existing species, egg-count, hatch-count and History fields are reusable.
  Actual names are `egg_type`, `egg_quantity`, and `eggs_hatched`, not
  `species`, `eggs_set`, or `hatched_count`.
- Current Start is **cloud-first**: save a session as `Active`, save settings,
  then show "Incubation Started!". That path does not wait for physical Uno Start.
- No implemented Android HC-05 bridge, durable confirmed-event queue, or offline
  batch synchronization was found in the inspected application source.
- The database does not yet have device/command/sample/event identifiers or a
  reliable distinction between physically Running and saved/synchronized state.
- Security is open: enabling RLS has not restricted these rows to the designated
  Android installation. Public sensor inserts and broad session/settings writes
  must be addressed before calling synchronization secure.
- A UI must separately show **Uno operating state**, **Bluetooth link**, **cloud
  sync state**, and **reading freshness**. "Running — not synced yet" is possible
  under approved offline Start; "saved in cloud" is not evidence of Running.

is required; consult the nullable column. Purpose descriptions come from app

```text
DELETE, INSERT, MAINTAIN, REFERENCES, SELECT, TRIGGER, TRUNCATE, UPDATE
```


### Startup/authentication

`lib/main.dart:16–31` loads environment configuration, initializes Supabase, and
awaits `signInAnonymously()` when no current session exists **before runApp**.
There is no offline error-handling path around this initialization. A first launch
without a cached session can therefore fail before the UI; this was not tested.
Existing cached-session availability is not a durable batch-event queue.

`supabase/config.toml:38–56` enables local signup/anonymous sign-in; hosted state
is UNKNOWN. Credentials themselves were not opened or printed.

### Current Start and Running behavior

1. Start handler sets an in-flight `_starting` guard and validates egg quantity
   (`lib/main.dart:2685–2707`).
2. It obtains the phone's `DateTime.now()`, calls `createSession()`, then calls
   `updateActiveSettings()` in a second request (:2709–2735).
3. The service performs a global Active-row pre-check then inserts `status:
   'Active'` and returns server-generated `id` (`supabase_service.dart:125–167`).
4. After successful cloud operations it navigates to IncubationStartedScreen
   (`main.dart:2737–2747`); that screen displays "Incubation Started!" and
   "Your eggs are now incubating" (:2840–2890).
5. No Bluetooth/Arduino START command or correlated physical RUNNING evidence
   is awaited by this handler. Thus saved/cloud success is treated as Start UI
   success. Existing database `Active` is not hardware status.

Double taps are guarded in the running UI instance, and the verified unique
partial index settles simultaneous Active insertions. Neither is durable command
idempotency. If the session insert succeeds but settings fails, a partial batch
remains; a subsequent attempt sees Active, not a reconciled hardware event. If a
response is lost, code cannot use a client-generated operation identity to find
the exact original successful request.

### Serial protocol and actual hardware claims

`lib/services/arduino_protocol.dart:191–211` encodes individual actuator commands
using `type`, `id`, `actuator`, `state`, not batch-level START/STOP events.
ACK fields and the explicit physical-verification limitation appear at :241–276.
Parser dispatch at :330–354 handles telemetry, ACK and LCD ACK, not dedicated
RUNNING/status/error families. Telemetry records phone receipt time at :147–175.

`lib/controllers/arduino_controller.dart:188–218` creates a timestamp/counter
actuator `id`, awaits an ACK and marks the command confirmed. The pending ACK map
and timeout are process-memory state in `arduino_serial_io.dart:128–159`; neither
is a durable Start/event store. They are not literal `command_id`/`batch_id` support.

`arduino_serial_factory.dart:1–10` selects flutter_libserialport for dart:io; that
does not implement Android Bluetooth SPP. `arduino_serial_stub.dart:14–15` describes
Windows USB support. `pubspec.yaml:10–17` has no direct Bluetooth package.
`android/app/src/main/AndroidManifest.xml:1–45` has no explicit Bluetooth permission
declarations. `android/.../MainActivity.kt:1–5` is a bare FlutterActivity. No native
Bluetooth implementation was found in the inspected app activity/source search.
Merged plugin permissions and actual Android behavior were not built/tested.

The application contains a global latest-reading SELECT but no sensor INSERT or

### History and day calculations

`getSessions()` returns every row ordered by `start_date` descending

`HistoryScreen._loadBatches()` maps rows to BatchData (`main.dart:4006–4022`).
Search/status/species/date filters are in-memory (:4025–4060), not a persistent

`activeIncubationScreenFor()` defaults an invalid start to `DateTime.now()`

Active screen uses elapsed `difference(...).inDays + 1`, clamped to species

### Manual hatch count and completion

The existing finish dialog requires an integer in `0..egg_quantity` and previews
a hatch rate (`main.dart:267–305`), then calls `completeSession()` (:313–326).
It currently returns 0.0 for zero original quantity (:303), which is not a valid
computed percentage for a zero denominator.

The service updates exactly the supplied `id` with `status='Completed'`,
`end_date`, and `eggs_hatched` (`supabase_service.dart:232–245`). It has no
server-side count validation, Active-status compare-and-set guard, returned-row
verification or immediate reread. A request resolving without an exception
causes the dialog to report success; affected-row count is not checked.
Physical STOP is not part of that code path. Repeated completion may overwrite
the count/end time. History later reloads rows, which is not an atomic verification
of the initial completion result. No automatic hatch counter was found here.

### Local persistence and offline synchronization

No application use of SQLite/Hive/SharedPreferences/file-backed event storage,

`pubspec.lock:499–553` includes shared_preferences transitively; package presence

also distinct from storing confirmed incubation events.

`IncubatorController.toSyncPayload()` (:575–600) is a map builder, not a database

## 6. Offline Start gap analysis against v0.4 + explicit approval

### What existing fields can support

**LIVE VERIFIED building blocks, not complete offline support:**

- `incubator_sessions.id`: keep existing server PK and History references.
- `egg_type`, `egg_quantity`, `eggs_hatched`, `end_date`: reuse their established
  meanings when synchronizing reviewed events/results.
- `status`: potentially reuse for a reviewed batch lifecycle; preserve legacy
  semantics rather than automatically interpreting `Active` as confirmed Running.
- `start_date`: candidate to represent confirmed original Start for future
  validated records, but current save-time semantics, missing timezone and legacy
  evidence must be addressed before reuse. Do not silently recertify historical
  values or overwrite them with reconnect/sync time.
- Existing numeric reading columns can hold values; provenance/validity and
  time distinctions still need reviewed additions or associated records.

**No current field set fully supports approved offline Start.** A server-generated
bigint ID cannot be obtained by the existing flow without a successful insert.
BY DEFAULT identity technically permits explicit IDs, but fabricating arbitrary
offline bigint IDs is not a collision-safe synchronization design.

### Missing mechanisms — not implemented

| Requirement | Current gap | Effect |
|---|---|---|
| Start while Bluetooth-connected but internet unavailable | Start waits for cloud create/settings; no HC-05 bridge | Offline-approved path absent |
| Stable identity before cloud contact | No cloud-independent batch key/command/event identity | Retry/reconnect cannot reliably match the same physical batch |
| Hardware Start proof | No stored correlated Uno evidence/time | Cloud Active may falsely imply Running |
| Durable pending confirmed events | No app outbox/storage transaction | App kill/reboot can lose in-memory evidence |
| Hardware persistence/status reconciliation | Not established by source/schema | Lost reply may lead to duplicate Start or unknown state |
| Idempotent synchronization | No unique external batch/event key or ingest RPC | Replays/conflicts cannot be resolved reliably |
| Event chronology vs current state | One Active partial index, no event log | Completed A then active B must reconcile in order without corrupting History |
| Source/time provenance | No device/batch/sample/measurement-validity fields | Late uploads can be wrong-batch or falsely live |
| Revocable authorized Android bridge | Open policies and anonymous startup | A second client can forge permitted writes |
| Profile identity/version | Text settings and unscoped row | Cannot prove Uno used the intended approved local profile |

### Duplicate/conflict risks

- At-most-one Active row is not exactly-once batch creation. Retrying after a
  response loss cannot locate the original operation by a stable request key.
- An offline confirmed batch may collide with an existing cloud Active row.
  Do not delete/complete either automatically to make the unique index pass.
- The same batch may be uploaded after completion; Active-only uniqueness cannot
  deduplicate Completed history or alternate status strings.
- Process-local actuator IDs and `_starting` guards do not survive app restart.
- Duplicate completions can rewrite reported counts and completion dates.
- Batch A events arriving after B must retain A's identity; upload order must not
  define ownership. A duplicate event must not trigger another physical command.

### Proposed synchronization direction — NOT IMPLEMENTED

1. Agree with Ally/Kath on an offline-allocatable batch identity, stable command
   and event IDs, actual Uno Start evidence, persistence and clock validity.
   Keep current bigint `id` as server PK; add a reviewed unique external mapping
   or associated identity mechanism rather than replacing existing IDs/History.
   Exact new names/types are intentionally not finalized by this audit.
2. Android durably records the pending request identity before sending START;
   after genuine confirmation durably retains original evidence/time and an
   unsynced event. If the reply is lost or the app restarts, query Uno status
   before retrying. Test the crash windows between send, confirmation and commit.
3. Show physical and sync facts independently: Start Pending/Unconfirmed;
   confirmed Running with sync pending; synchronized record; reconciliation
   conflict. Synced history is not automatically a current physical heartbeat.
4. Once online and authorized, upload the same event identities to a reviewed
   transactional ingestion operation. Authenticate Android, validate bound source/
   batch/profiles, deduplicate, preserve hardware time and separately record
   server receipt. Never manufacture measurement time or physical evidence.
5. Return a durable committed receipt/mapping. Mark local events synced only
   after verifying that receipt; ambiguous outcomes retry/reconcile by identity.
   Apply reviewed retention; do not discard the only unsynced evidence early.
6. Preserve order/relationships for offline A-completed and B-started events.
   Resolve conflicting cloud state deliberately; do not remove the global
   safeguard or rewrite another batch just to accept a replay.
7. Verify unauthorized/forged/revoked uploads, direct-table bypasses, duplicates,
   network loss, phone restart, and source-to-row matching in `smarthatch-test`
   after explicit reviewed setup. No service-role key in Android or Bluetooth.

This is approved offline-Start **design work still to implement/test**, not an
assertion of a working queue. Continuous sensor backfill/background execution is
not implied. Offline physical authorization and cloud revocation are separate:
a disconnected phone cannot learn an immediate server revocation. The acceptable
offline operating procedure, credentials/cached authorization, and retention of
events rejected after revocation need explicit review; cloud rejection must not
